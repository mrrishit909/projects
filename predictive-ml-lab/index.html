PREDICTIVE

Real scikit-learn churn model, FastAPI, React prediction studio with SHAP explainability and a drift monitor.

Python · scikit-learn · FastAPI · Pydantic · SHAP · React · Vite · TypeScript · Tailwind CSSCode on GitHub ↗

Built as a vertical slice of a 10-app enterprise master-prompt (originally specified Optuna, MLflow, Docker Compose, Postgres/Redis, CI, Sentry, and a literal 3-agent build team). Every piece that changes what the app predicts or evaluates is real; infrastructure that exists only to operate the app at production scale was substituted or skipped and documented in the repo's LIMITATIONS.md, rather than silently dropped.

01 — The problem

Telecom companies lose revenue to customer churn, and want to know: which customers are likely to leave, and why? This project builds a real, evaluated machine-learning answer rather than a dashboard mockup: train a model on the public IBM Telco Customer Churn dataset, calibrate and explain it, and serve it behind an API a real frontend can call.

02 — What I built

An end-to-end ML application, not a notebook:

  • Training pipeline (ml/train.py): a stratified 80/20 holdout, 5-fold cross-validation fit only inside the pipeline (no leakage), three real candidate models (Dummy, LogisticRegression, HistGradientBoosting), the best one isotonic-calibrated, and real SHAP values computed on the test set.
  • FastAPI service with Pydantic-validated /predict, /predict/batch, /explain/global, /explain/local, /drift endpoints — malformed input (missing fields, NaN, negative tenure, invalid enums, oversized batches) returns 422, not a silent wrong answer.
  • React/Vite/Tailwind frontend with a canvas decision-boundary intro animation (skip + reduced-motion supported), a prediction studio, an explainability view (exact training-time SHAP + a fast live local approximation), a model-comparison table, and a drift monitor that is clearly labeled as a synthetic simulation, not live telemetry.
  • 18 pytest tests covering model reproducibility (no leakage, beats the dummy baseline) and the API's negative-input gate.

03 — How it was built

  1. 01

    Get the real data and define one feature contract

    Downloaded the public IBM Telco Customer Churn CSV (7,043 customers) and wrote ml/schema.py as the single source of truth for feature names and allowed categories, imported by both the training pipeline and the API's Pydantic model, so the model can never be trained on a column the API doesn't send.

  2. 02

    Train three real models without leaking the test set

    A stratified 80/20 split is held out before anything else touches the data. Preprocessing (scaling, one-hot encoding) is fit fresh inside a scikit-learn Pipeline, refit per cross-validation fold, so the reported test metrics can't be inflated by information leaking from the test rows.

    dummy:                   ROC-AUC 0.500 (most-frequent baseline)
logistic_regression:     ROC-AUC 0.842
hist_gradient_boosting:  ROC-AUC 0.833
logistic_regression_calibrated: ROC-AUC 0.841, Brier 0.139 (shipped model)
  3. 03

    Calibrate the shipped model and explain it with real SHAP

    Raw classifier scores from scikit-learn aren't well-calibrated probabilities, and this app shows a probability directly to the user, so the winning model is wrapped in CalibratedClassifierCV (isotonic). Global SHAP values are computed once at training time; a cheap perturbation-based local explanation runs per live prediction to keep API latency low — the UI labels which is which.

  4. 04

    Build the FastAPI service with a real negative-input gate

    Every endpoint validates through Pydantic: out-of-range numbers, invalid category values, NaN/infinity, missing fields and oversized batches (>500 customers) all return HTTP 422. A synthetic, explicitly-labeled drift simulator shifts a fake customer cohort over 30 days and flags when predicted churn rate moves more than 15%.

  5. 05

    Build the React frontend and verify it live

    A canvas-based decision-boundary intro (customer points separate into churn/stay regions) hands off into four tabs: Prediction studio, Explainability, Model comparison, Drift monitor. Verified by actually running both dev servers and driving the UI in a real Chrome tab — not just a production build that compiles.
