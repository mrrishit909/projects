01 — The problem

Telecom companies lose revenue to customer churn, and want to know: which customers are likely to leave, and why? This project builds a real, evaluated machine-learning answer rather than a dashboard mockup: train and tune a model on the public IBM Telco Customer Churn dataset, calibrate and explain it, optimize its decision threshold against a business cost model, and serve it behind a real API and frontend with authentication, logging, and rate limiting.

02 — What I built

An end-to-end ML application with a full remediation pass, not a notebook:

  • Training pipeline (ml/train.py): a stratified 80/20 holdout, 5-fold cross-validation fit only inside the pipeline (no leakage), Optuna-tuned HistGradientBoosting (25 trials, CV-only), three baseline models, isotonic calibration, real SHAP (TreeExplainer/LinearExplainer, exact for whichever model wins, a real bug where the SHAP values were computed in the wrong feature space was found and fixed mid-build), and a business-cost-optimal decision threshold chosen from out-of-fold predictions on the training split only, never the test set.
  • MLflow experiment tracking (local file store) logging every candidate model's params and metrics.
  • FastAPI service with Pydantic validation, API-key authentication on the two write-adjacent endpoints, PostgreSQL prediction logging (degrades cleanly if the DB is unreachable), and a Redis-backed rate limiter, all three verified live against a real Docker Compose stack, not just unit-tested.
  • React/Vite/Tailwind frontend with a canvas intro that does a genuine camera zoom into one selected point before morphing into the real form (an earlier plain-fade version was replaced after review), a prediction studio, an explainability view, a model-comparison table, and a drift monitor explicitly labeled synthetic.
  • 29 pytest tests plus a real Playwright + axe-core browser suite and a Vitest frontend unit suite.

03 — How it was built

  1. 01

    Get the real data and define one feature contract

    Downloaded the public IBM Telco Customer Churn CSV (7,043 customers) and wrote ml/schema.py as the single source of truth for feature names and allowed categories, imported by both the training pipeline and the API's Pydantic model.

  2. 02

    Train, tune, and track three real models without leaking the test set

    A stratified 80/20 split is held out before anything else touches the data. Optuna searches HistGradientBoosting's hyperparameters using only cross-validated ROC-AUC on the training split; MLflow logs every candidate run.

    dummy:                                ROC-AUC 0.500
logistic_regression:                  ROC-AUC 0.842
hist_gradient_boosting (Optuna-tuned): ROC-AUC 0.846  (was 0.833 untuned)
hist_gradient_boosting_calibrated:     ROC-AUC 0.845, Brier 0.136 (shipped model)
  3. 03

    Fix a real SHAP bug, then optimize the decision threshold against cost

    An independent review caught that the shipped model's SHAP values had been computed with a permutation-importance fallback zipped against the wrong feature-name array, the published bars were mislabeled. Fixed to always compute exact SHAP (TreeExplainer or LinearExplainer) in the same transformed feature space the names come from, with an assertion guarding the array-length match. Separately, a business-cost threshold (illustrative FN=$500 / FP=$50) is chosen from out-of-fold training predictions only, a dedicated test asserts the selection code never references the test split.

  4. 04

    Add real auth, logging, and rate limiting, verified against live Docker containers

    X-API-Key auth, PostgreSQL prediction logging, and Redis-backed rate limiting were each verified against actually-running containers: a request without a key gets a live 401, a logged prediction was queried back out of Postgres, and the 61st request in a window got a real 429. An independent verification pass then found and fixed two real bugs this introduced: a stray CLI line in requirements.txt that broke every fresh Docker build, and a frontend that forgot to send the new auth header entirely, both confirmed fixed by rebuilding from a clean docker compose down -v.

  5. 05

    Automated browser verification, not just manual screenshots

    A real Playwright + axe-core suite now runs against the live app (intro → form reveal, a full predict-and-see-result flow, an accessibility scan, mobile/desktop/reduced-motion checks), plus a Vitest unit suite for the frontend client code.
