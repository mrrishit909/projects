01 — The problem

A text-to-SQL chatbot is only as trustworthy as what stops it from doing damage when the model is wrong, tricked, or confidently makes something up. The interesting engineering problem isn't getting an LLM to write SQL, it's building the gate that doesn't depend on the LLM behaving, and proving that gate actually holds under real adversarial attack, not just against the test cases its own author thought to write.

02 — What I built

A full pipeline on real PostgreSQL 17, with three independent layers of defense:

  • A least-privilege Postgres role (querymind_reader): SELECT on the 5 approved views only, zero grant on the 4 base tables, governed by real Row-Level Security policies that still hold even against an accidental grant (proven live).
  • A real query-execution timeout (3s, role-level statement_timeout), not a lock-wait bound like the earlier SQLite build's busy_timeout, which doesn't actually stop a running query. Proven against both a raw pg_sleep(10) and a real validator-accepted expensive query.
  • An AST allowlist validator (sql_validator.py, sqlglot + PostgreSQL dialect) that accepts only a single SELECT/CTE referencing approved views and an explicit function allowlist, default-deny, not a denylist, so pg_sleep/dblink/set_config/anything unrecognized is rejected by construction.
  • A read-only transaction (SET TRANSACTION READ ONLY) as a third, independent backstop, proven to block a write even for a role that could otherwise write.
  • SSE streaming (/ask/stream: generating_sql → validating → executing → answer), Monaco-rendered SQL, a Recharts visualization alongside the result table, and sanitized Markdown rendering.

03 — How it was built

  1. 01

    Migrate to real Postgres with a role that can't query anything by accident

    The 5 approved views are owned by a dedicated, RLS-governed role, deliberately NOT created with security_invoker=true as the spec literally asked for, because that setting was tested live and proven to make every query fail (it checks the querying role's own base-table grants, and the reader role has none by design). The documented pre-PG15 alternative, a definer-rights view owned by a separate, non-superuser role that RLS still governs, closes the same risk without breaking the app.

  2. 02

    Rebuild the validator as a function allowlist, not a denylist

    The SQLite build denylisted a handful of named functions. On Postgres that's unsafe: there are too many dangerous functions to name them all. The rewritten validator allowlists only the sqlglot node classes the 5 views actually need, anything else, including every function sqlglot doesn't recognize, is rejected by default.

    validate_sql("WITH d AS (DELETE FROM v_orders RETURNING *) SELECT * FROM d")
-> ok=False, reason='disallowed statement type in query: Delete'

validate_sql("SELECT pg_sleep(1)")
-> ok=False, reason='disallowed function: pg_sleep'
  3. 03

    An adversarial verification pass found a real, live bypass

    A separate verification subagent attacked the rebuilt validator directly and found that its CTE-name-shadowing defense checked only the bare table name, never whether the reference was schema-qualified. WITH pg_roles AS (SELECT 1 FROM v_customers) SELECT rolname, rolsuper FROM pg_catalog.pg_roles was wrongly accepted, confirmed live through the real /execute endpoint, returning actual Postgres role data including superuser flags, plus a full information_schema table enumeration via the same technique. It never reached business data or allowed writes (the role's own grants still blocked those), but it fully defeated the allowlist for Postgres catalog objects.

  4. 04

    Fixed the same day, re-verified against a rebuilt live container

    A table reference is now treated as a CTE match only when it is both unqualified and name-matches a locally-visible CTE; any schema-qualified reference is always checked against the approved views regardless of a same-named CTE. Two lower-severity documentation mismatches found in the same pass (window functions, the || concat operator) were closed the same way. The exact original attack was re-sent to a freshly rebuilt Docker container and now returns "rejected"; a legitimate query was confirmed to still work on the same container.

04 — Results

87/87 tests passed, 2 skipped (real-LLM tests, skip cleanly without an API key): 36 SQL-validator adversarial cases, 10 live Postgres role/RLS/timeout proofs, 12 independent adversarial-verification cases (including the 4 that pin the exact bypass above as a permanent regression test), plus the pre-existing read-only-transaction and API test suites. Full fresh-checkout docker compose down -v && up -d --build verified end to end: health check, SSE streaming, Redis rate limiting (20 requests allowed, the 21st got a real 429 with the counter key visible in Redis), and the exact catalog-leak attack confirmed blocked on the rebuilt container.
